# HoneyForge — Архитектура

## 1.1. Общая идея

HoneyForge — распределённая платформа ловушек, состоящая из **трех физически и сетево разделённых контура**:

- **Контур центра (Control Plane)** — изолированный сервер: Control API, хранилище,
  realtime-слой, Web UI, пограничный Nginx. Из сегмента приманок напрямую недоступен.
- **Контур ловушек (DMZ)** — хост(ы) с агентами: эмулируемые сервисы и скрытый агент,
  который пишет телеметрию в локальную очередь.
- **Канал управления** — двусторонний TLS-канал между агентом и центром: агент
  забирает конфигурацию и отдаёт события под видом обычного CDN-контента.

Ключевой принцип: **атакующий не должен понять, что попал в ловушку**, а трафик
агента не должен выглядеть как «телеметрия honeypot'а».

## 1.2. Компоненты

### Контур центра

| Компонент | Роль | Где живёт |
|---|---|---|
| **Nginx** | TLS-терминация, reverse-proxy, разделение контуров, маскировка канала агентов под CDN-хост | Control Plane, единственный контейнер с опубликованными портами |
| **Control API** (FastAPI) | Профили, ловушки, события, аутентификация, выдача конфигурации агенту, приём телеметрии, экспорт IoC | Control Plane |
| **pg_listener + WS Manager** | `LISTEN/NOTIFY` → перезагрузка события из БД → рассылка в WebSocket `/ws` | Control Plane |
| **PostgreSQL** | Хранилище: 6 таблиц, триггер `NOTIFY`, индексы расследования | Control Plane |
| **Web UI** | Статика (vanilla JS): обзор парка, лента событий, ловушки, конструктор профилей | Control Plane |
| **Collector** | Отдельный процесс стека центра. **Сейчас — заглушка**: держит контейнер живым и пишет heartbeat раз в 30 с; приём и нормализация выполняются внутри API (ADR-0006) | Control Plane |

### Контур ловушек

| Компонент | Роль | Где живёт |
|---|---|---|
| **Agent Low** | SSH/HTTP/MySQL/UDP: баннеры и простые ответы, фиксация факта взаимодействия | DMZ |
| **Agent Medium** | Fake SSH с командной строкой, fake HTTP админка, fake-БД с разбором SQL и fake-FS | DMZ |
| **Очередь событий** | SQLite на хосте агента: буферизация при потере связи, дослылка, карантин переполнения | DMZ |
| **Артефакт `relay.pyz`** | Нейтральный zipapp со всем кодом агента; на хосте ловушки лежит один файл | DMZ |

## 1.3. Потоки данных

**1) Атакующий → ловушка.**
Сканер или эксплойт попадает в эмулируемый порт. Ловушка отвечает правдоподобно
(баннер, тело страницы, приветствие shell) и превращает каждое наблюдение в
**Security Event**. Общий конверт события: `id`, `schema_version`, `trap_id`,
`attack_session_id`, `event_type`, `observed_at`, `source_ip`, `source_port`,
`target_service`, `target_port`, `payload`. Полный контракт — `docs/event_contract.md`.

**2) Ловушка → центр (телеметрия).**
Агент складывает события в локальную очередь и отправляет батчи на
`POST /assets/v2/init`. Путь, `Content-Type: application/javascript` и имя виртуального
хоста `assets.cdn-static.example` делают канал неотличимым от обращения к статике CDN.
Каденцию агент берёт из профиля ловушки (см. §1.5).

**3) Центр → БД → лента событий.**
API валидирует батч, дедуплицирует по `id` и пишет событие и Attack Session в
`security_events`/`attack_sessions`. Триггер PostgreSQL отправляет `NOTIFY` с UUID
события по каналу `security_events`; listener перечитывает полную запись из БД и
пушит её в WebSocket. В UI событие появляется без перезагрузки страницы; при разрыве
соединения страница догружает пропуск через REST по курсору.

**4) Оператор → центр.**
Логин (`POST /api/v1/auth/login` → JWT в httpOnly-cookie) → конструктор профилей →
регистрация ловушек и управление их жизненным циклом → расследование событий с
фильтрами → экспорт IoC в CSV теми же фильтрами
(`GET /api/v1/security-events/export.csv`).

## 1.4. Сетевая изоляция

| Сеть | Кто в ней | Что доступно |
|---|---|---|
| `honeyforge_mgmt_net` (internal, `172.30.0.0/24`) | API ↔ PostgreSQL ↔ Collector ↔ Web | Наружу — ничего; наружу выходит только Nginx |
| `honeyforge_edge_net` | Nginx Control Center | Единственная сеть центра с опубликованными портами (`CENTER_HTTP_PORT`, `CENTER_HTTPS_PORT`; в demo — 8443) |
| `relay_egress_net` (`172.29.0.0/24`) | Агенты ловушек | Только исходящий TLS к адресу Control Center |
| `relay_service_net` (internal, `172.31.0.0/24`) | Агенты ↔ их эмулируемые порты | Внутренняя сеть без внешнего маршрута; каждый агент слушает только свой адрес (`172.31.0.11` / `172.31.0.12`) |

Следствия:

- Внутренние адреса БД агентам неизвестны; у них есть только URL канала и CA.
- Удаление ловушки (`DELETE /api/v1/traps/{id}`) не «течёт» за её пределы: агент
  теряет доступ к центру и через health-timeout уходит в `offline`.
- Канал агента терминируется на **опубликованном** порту центра, поэтому из сегмента
  приманки он достижим; скрытность держится на имени хоста, TLS и отсутствии
  маркеров в артефакте (см. §1.5), а не на сетевой недоступности.

## 1.5. Что маскируется

| Что | Как |
|---|---|
| Endpoint телеметрии | URI `/assets/v2/*` под отдельным виртуальным хостом `assets.cdn-static.example`, `Content-Type: application/javascript` |
| Тайминги beacon'а | `masking.beacon_interval_seconds` ± `masking.beacon_jitter_seconds` из профиля ловушки (демо: 5 с ± 2 с); без настроек агент берёт `DELIVERY_INTERVAL_SECONDS` и джиттер 30 % |
| Размер запросов beacon'а | Случайный батч 40–100 % от лимита, чтобы соседние запросы отличались по весу |
| User-Agent агента | `masking.user_agent` из профиля; пустое или некорректное значение игнорируется, остаётся дефолтный клиент urllib |
| Процесс агента | `prctl(PR_SET_NAME)` + перезапись `argv`: в `ps`, `/proc/*/comm` и `/proc/*/cmdline` — нейтральное имя (`syslog-relay`, настраивается `PROCESS_MASK_NAME`); значение с маркером игнорируется |
| Содержимое артефакта `relay.pyz` | `agent/build_bundle.py` переименовывает модули (`listeners.py`, `runtimekit.py`, `relay_common/*`) и переменные окружения (`TRAP_SECRET_FILE` → `SERVICE_KEY_FILE`), **вырезает все комментарии и докстринги**; словарь запрещённых имён собран из фрагментов |
| CN сертификата на хосте ловушки | Нейтральный (`/CN=Local Demo CA`), потому что CA-файл смонтирован агенту и доступен атакующему с root |
| Баннеры и тела сервисов | Реалистичные строки (`OpenSSH_8.9p1`, `nginx/1.24.0`, `5.7.42-MySQL`); тело Low-HTTP собирается из объявляемого баннера, приветствие fake-shell — нейтральная строка Ubuntu |
| Тайминги ответов | `response_delay_ms` из профиля плюс случайный разброс `response_jitter_ms` — каждый ответ получает свою паузу |

**Граница маскировки (честно):** внутри `relay.pyz` остаются слова `trap_id`,
`agent_version`, `decoy_credentials` — это ключи контракта Control Center ↔ Agent, их
переименование сломало бы выдачу конфигурации. Регрессия «в артефакте нет слов про
honeypot» закреплена в `tests/test_bundle_masking.py`.

## 1.6. Где принимаются решения

- **Приём и запись телеметрии — внутри API** (ADR-0006): один транзакционный путь,
  advisory-lock по `trap_id`, `INSERT … ON CONFLICT DO NOTHING` по `id`.
- **Realtime — через PostgreSQL**, а не через шину: `NOTIFY` несёт только UUID,
  источником правды остаётся строка в таблице.
- **Collector пока не участвует в приёме** (ADR-0006 сохранён частично, решение D2
  принято, но не реализовано).

## 1.7. Не реализовано

| Что | Статус |
|---|---|
| Оркестратор «развернуть ловушку одной кнопкой» (FR-C6) | Нет. Есть сборка артефакта и установщик для нативных хостов, но нет API, доставки на удалённый хост и кнопки в UI |
| Алерты и правила (FR-C7) | Нет. Реализована только вторая половина требования — экспорт IoC в CSV |
| Honeytokens (FR-A6) | Нет: ни модели, ни детектора, ни события `honeytoken_triggered` |
| Geo/ASN, агрегаты, топ источников | Нет. `/api/v1/dashboard` — заглушка, интерфейс считает счётчики статусов в браузере |
| Экран журнала аудита | Данные пишутся при каждом изменении и при отказе по правам, но **читающего API и страницы нет** |
| mTLS, pinning, ротация клиентских ключей (MASK-7) | Нет. Аутентификация агента — bearer-секрет поверх TLS с проверкой CA |
| High-interaction (FR-A5) | Исключено заказчиком: уровня `high` нет ни в БД (`CHECK`), ни в UI |

Источники истины: `docs/architecture.mmd` (схема), `docs/database.md` (схема БД),
`docs/event_contract.md` (контракт события), `docs/deployment.md` (развёртывание).
